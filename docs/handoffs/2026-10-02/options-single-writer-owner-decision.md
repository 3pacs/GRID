# Options automatic writer policy — owner decision, draft only

No approval, merge, deployment, environment change or scheduler activation is implied by this proposal.

October 2 evidence: the protected daily scheduler captured 122/203 tickers and 66,587 rows (13:35–13:43 UTC). SmartScheduler repeated the same scope at 13:39–13:48; Hermes `_retry_source(yfinance_options)` repeated it at 13:57–14:06. Batch metadata records three batches per successful ticker, 199,761 rows, all labeled `options_puller`. GEM independently captured eight tickers / 4,082 rows at 13:43–13:44. The later automatic repair can outrank GEM in the default latest-batch view. October 1 already holds 2,524 options_puller batches / 1,382,367 rows across only 122 tickers. Suppressing only Hermes REPULL leaves the SmartScheduler writer active.

Proposed owner choice: make the daily scheduler the primary automatic full-universe writer, with the already approved explicit GEM subset as an exception. SmartScheduler and Hermes repairs observe registered non-GEM batch counts and return SKIPPED / zero new writes; neither reports the source fresh. This draft is disabled by default (`GRID_OPTIONS_AUTOMATIC_WRITER_POLICY=legacy` or unset). An owner could separately choose `daily_scheduler` after review and approve a future controlled Hermes activation. This document is not an instruction to set that variable now.

The guard runs before either secondary path constructs OptionsPuller, authenticates to Yahoo or publishes source_catalog freshness/backlog. Partial daily coverage remains partial. An empty or unavailable batch query also defers: a fallback capture could race the daily scheduler while it fetches its first ticker. This deliberate restriction closes that race without changing the protected scheduler or adding migrations/locks. No automatic repair is permitted under this policy when the daily writer fails; a replacement capture would need a separate owner decision. Already running workers are not cancelled by this draft.

The metadata query is read-only with five-second statement and one-second lock bounds. Counts exclude `gem`, but `options_puller` is shared provenance and cannot prove scheduler ownership. The policy assigns ownership; it does not infer it from existing labels. Future distinct labels for the primary and repair writers would need their own reviewed change and protected-scheduler activation approval. No legacy rows are relabeled or deleted, and no provenance gaps are hidden.

Validation is local, mocked, without production writes/provider calls: defaults preserve legacy behavior; empty/in-flight/partial/repeated coverage always defers; query failures and invalid settings fail closed; both secondary paths stop before construction; skipped repairs remain non-fresh; explicit GEM still captures its subset. Existing options deadline and Hermes abandonment/accounting tests are retained.

OWNER QUESTION: accept primary daily-scheduler ownership with explicit GEM exception and secondary observation only, including no automatic fallback after a primary failure? This PR remains draft and must never merge/activate under the ordinary app-only authorization.
